# Trainer

The trainer has two layers: a **headless core** (spot generation, bots, rollouts, stats) with no raylib dependency, so it is unit-testable, and a **raylib GUI** on top.

## Core

- Each hand: deal 6 hole cards, simulate bots up to the user's decision point, show the spot, and take the user's choice (F/C/R).
- **Spot filtering:** `deal()` reject-samples hands until the user's seat reaches a decision of the requested type and position. Bots, and the user's own earlier decisions in the hand, play from the strategy. Spot types are by what the user faces: open (unopened pot), vs open, squeeze (an open plus callers), vs 3-bet, vs squeeze (the user cold-called and someone 3-bet), and vs 4-bet+. A type/seat that can never occur (e.g. vs squeeze at UTG or BB) returns nothing after the try limit.
- Bots sample their actions from the strategy's average for their (history, hand): a solve, or charts written over one (chart modes below). This keeps them mixed and lets them respond sensibly to off-equilibrium user lines.
- **Feedback:** do not read action values from sampled regrets (too noisy). Instead, for the user's actual hand, roll out every legal action on the same opponent deals, with all bots following the strategy, and report EV in bb per action plus EV loss of the user's choice versus the best action.
  - Each rollout **re-deals the opponents' hands** from the deck minus the user's cards. Do not use the hands the bots actually hold, since that leaks hidden information and adds variance.
  - Weight each rollout by the probability that the bots would have taken the observed history with those hands: the product, over prior bot actions, of `sigma(history_k, bucket(hand))[action_k]`. Ignoring the history gives wrong EVs because the ranges are wrong. Weighting (importance sampling) is simpler and lower-variance than rejection.
  - Rare histories leave few deals with weight: pure charts rule out most deals, and a handful of weighted deals cannot carry a mean when one of them is an all-in pot. So a rollout deals a minimum number of times, then keeps dealing until the effective sample size $(\sum w)^2 / \sum w^2$ reaches a target, or a deal cap is hit (`RolloutConfig`). Deals with weight 0 cost almost nothing. It reports a standard error per action, and per difference between actions (all actions share the deals, so differences are much more precise). Grading does not count a choice as a mistake when its EV loss is within about 2 standard errors.
  - After the user's choice, everyone, the user included, plays on from the strategy. For hands that never reach a spot in the solve's average, the strategy there is the regret-matched one from the solver, not uniform (`Solver::average`).
  - Terminal payoffs use the same utility code as the solver.
- Also show the strategy's mix for the user's hand (e.g. "3-bet 35% / call 65%") and the bot range for context.
- Track stats per spot type and position: average EV loss, accuracy, and most-leaked spots. The GUI keeps a separate set per strategy mode.
- Accept as "correct" any action with strategy frequency or EV loss below a configurable threshold, or a loss within the rollout's noise (`GradeConfig`; mixed strategies mean several actions can be fine).
- **Strategies:** *Scratch* is our solve from scratch. *Anchored* is a solve with the GTO charts (`ref/`) frozen (`solve --lock`), so every uncharted spot is solved by our method against them.
- **Chart modes (GTO, PTO):** built by overwriting every spot that has a reference chart in the mode's directory (`ref/`, `ref/pto/`) with that chart (`applyCharts`, `src/solver/strategy.h`; `scope: listed` charts overwrite only the classes they name). Both use Anchored as the base, so PTO's gaps are filled by play anchored on the GTO charts; without an Anchored solve both fall back to Scratch. The charts are re-applied over Anchored anyway, which gives the charted-entry mask and picks up painter edits. Bots, rollouts and grading all use this strategy, so the user trains against chart-playing opponents. Where the chart decides the user's hand, grading ignores EV: an action is correct iff the chart plays it at least 10% of the time. Rollout EVs are still shown, valued against the chart-playing bots. Where the solve decides, the usual grading applies.

## GUI (raylib)

- A table view: seats, stacks, positions, bets in front of players, pot, the user's hole cards, and fold/call/raise buttons labelled with amounts. Keyboard shortcuts too (F/C/R, space for next hand). Bots act after human-like think times that don't depend on the hand. The window is laid out at a fixed size and scaled to 80% of the screen height.
- A feedback panel after each decision: EV per action and the EV loss, each with its standard error (omitted when exact), a "low sample" note when the rollout hit its deal cap before the target sample size, the strategy's mix for the hand, and a 13×13 range grid for the relevant bot or for the user's spot.
- A spot picker (spot type, position), a stats screen, the chart painter (`E`, docs/validation.md) and a realization inspector (`I`: R per hand class for a chosen position (IP/OOP), role, pot type and SPR).
- `T` cycles Scratch / GTO / PTO, skipping chart modes with no charts. It takes effect at the next hand, because rollouts on the worker thread read the current hand's strategy. A badge shows the mode (and the pending one), the mix is labelled with where it comes from (GTO, PTO, Anchored or Scratch), and an uncharted decision in a chart mode is marked "no chart" plus the solve it falls back to. The painter edits the GTO charts; closing it reloads both chart modes, after any running rollouts finish.
- Buttons and panels are drawn with plain raylib calls (a small immediate-mode button helper); cards are rectangles with text and suit shapes.
- Rollouts take noticeable time. Run them on a worker thread and keep the UI loop responsive.
